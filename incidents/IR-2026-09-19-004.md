## Remediation

1. File removed: `Remove-Item ...\Startup\update.exe`
2. Registry key deleted: `Remove-ItemProperty HKCU:\...\Run -Name SystemUpdate`
3. Check both machine-level Startup (`%PROGRAMDATA%`) and user-level (`%APPDATA%`) — only per-user vector used here
4. Check HKLM Run key as well — not used here but common dual vector:

```powershell
# Verify no remaining Run key entries
Get-ItemProperty "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run"
Get-ItemProperty "HKLM:\Software\Microsoft\Windows\CurrentVersion\Run"

# Verify Startup folder is clean
Get-ChildItem "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup\"
```

## Lessons Learned

- Wazuh FIM realtime on Startup folders is the fastest detection — fires in under 1 second of file drop, before any reboot
- Two vectors (folder + registry) generate two independent alerts — correct SOC behavior is to correlate them by timestamp and agent, not treat as unrelated
- `update.exe` naming pattern is textbook masquerading (T1036) — process name inspection alone would miss this; path context matters
- The Run key under HKCU (per-user) requires no admin rights — any unprivileged process can write there; this is a significant low-bar persistence technique
- FIM Rule 750 on `CurrentVersion\Run` means attacker cannot use this registry key without generating an alert — registry monitoring is as important as file monitoring for T1547.001
